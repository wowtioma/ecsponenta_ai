# Экспонента · Синоникс

Ветка `integration` объединяет ядро расчёта (`A`), работу с моделью и базой знаний (`B`) и интерфейс (`С`). Ядро принимает структурированное описание обмена между двумя сетями, рекомендует размещение межсетевого экрана и «Синоникса», рассчитывает правила и формирует уточняющие вопросы. Расчёт работает локально и даёт одинаковый результат для одинакового входа.

## Что реализовано

- **Состояние сессии.** `Session` хранит сети, потоки, явно согласованные допущения и ответы на уточнения. Неизвестные параметры попадают в `unknowns`, согласованные решения — в `assumptions`.
- **Размещение.** Рекомендуемая цепочка проходит от открытой сети через МЭ и «Синоникс» к закрытой сети. Узел А обращён к открытой стороне, Узел В — к закрытой. USB подключается к Узлу А и на диаграмме проходит мимо МЭ.
- **Расчёт данных.** Потоки с общим получателем, портом и протоколом могут использовать одно правило. MQTT, Modbus TCP и МЭК‑104 требуют двунаправленного правила. NTP рассчитывается как одно однонаправленное правило и выгружается как UDP. При превышении 256 правил ядро возвращает ограничение и сохраняет полный расчёт.
- **Расчёт файловых потоков.** Ядро учитывает проверки на каждой стороне, видимость принятых файлов и совместимость настроек PULL/PUSH. В счётчике файловых пользователей один человек учитывается один раз по идентификатору, каждое правило с PULL добавляет одного технического пользователя, PUSH дополнительных пользователей не добавляет.
- **Уточнения и выгрузка.** Вопросы содержат варианты «Не знаю» и «Другое». Служебный результат версии `1.1` содержит размещение, правила, счётчики и статус `needs_clarification`, `preliminary`, `completed` или `unsupported`.

## Общая локальная сборка A, B и C

Для прогона нужны Python 3.10+, Node.js, исходный ZIP организаторов и ключ Groq.
В корне создайте локальный файл `.env` со строками `LLM_PROVIDER=groq`,
`GROQ_MODEL=openai/gpt-oss-120b` и `GROQ_API_KEY=<ваш ключ>`.
Ключ и ZIP хранятся локально.

**Важно про базу знаний.** Папка `Кейс АйТи Бастион — Синоникс/` не входит
в репозиторий (она в `.gitignore`), а RAG ищет `synonyx_base/*.md` в ней.
На чистом клоне укажите путь явно — в `.env` или переменной окружения:

```powershell
$env:SYNONYX_BASE_DIR = 'C:\путь\к\Кейс АйТи Бастион — Синоникс\synonyx_base'
```

Без этого сервер завершится с понятной ошибкой, а тесты `tests/test_rag.py`
упадут на пустой базе. Если архив организаторов распакован, `SYNONYX_BASE_DIR`
можно не задавать: сервер возьмёт `synonyx_base/*.md` прямо из ZIP.

В первом PowerShell запустите API из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt 'pydantic>=2,<3'
$env:SYNONYX_BASE_DIR = 'C:\путь\к\Кейс АйТи Бастион — Синоникс\synonyx_base'
$env:SYNONYX_CASE_ZIP = 'C:\путь\к\архиву.zip'
.\.venv\Scripts\python.exe integration_test_server.py
```

`SYNONYX_CASE_ZIP` нужен, только если `SYNONYX_BASE_DIR` не задан. Тесты:
`.\.venv\Scripts\python.exe -m unittest discover -s tests`.

Во втором PowerShell запустите интерфейс из корня той же копии:

```powershell
cd frontend
npm.cmd ci
$env:VITE_USE_MOCK = 'false'
npm.cmd run dev
```

Откройте адрес Vite и отправьте полное описание F02 или вопрос Q01.
Уточнения формирует ядро по шаблонам. Название потока и получателя сервер
подставляет из данных сессии, дополнительных вызовов Groq для вопросов нет.
Сервер по умолчанию слушает порт 8000. Если он занят, задайте
`SYNONYX_API_PORT` для сервера и соответствующий `SYNONYX_API_TARGET` для Vite.

Для прогона открытых сценариев запустите из корня проекта
`python scripts/audit_integration.py` с переменной `SYNONYX_CASE_ZIP`.
Скрипт использует интерфейсный прокси на порту 5173. Для другого адреса
задайте `SYNONYX_TEST_URL`. Результаты лежат в `sessions/audit_results.json`,
журналы модельных вызовов сохраняются в `sessions/`.

Это локальная сборка для промежуточной проверки. В предыдущем прогоне
F04, F07 и N05 требовали доработок. Ставки в журнале нужно сверить со
снимком OpenRouter для выбранного варианта Groq перед итоговой проверкой.

## Редактирование схемы

В разделе «Схема» можно менять оформление и расположение объектов в редакторе draw.io. Сохранённые правки относятся к текущей сессии и конфигурации. Они видны в режиме «Просмотр» и входят в скачиваемый файл `.drawio`. Кнопка «Сбросить» возвращает схему по расчёту.

Колесо мыши масштабирует схему вокруг курсора, перетаскивание перемещает её внутри области просмотра. Кнопка «Показать целиком» возвращает масштаб и положение к исходному виду.

Расчёт правил и служебный JSON формируются по данным из чата. Чтобы изменить правила обмена, уточните параметры в чате.

Если `embed.diagrams.net` недоступен, просмотр показывает схему по расчёту, а скачивание использует последний сохранённый XML. Для собственного редактора укажите `VITE_DRAWIO_EMBED_URL` в настройках фронтенда.

## Локальные ключи Groq

При `LLM_PROVIDER=groq` по умолчанию используется `GROQ_API_KEY`.
Чтобы сменить ключ при ротации учётных данных, заполни нужные строки
`GROQ_API_KEY_1`, `GROQ_API_KEY_2`, `GROQ_API_KEY_3` в локальном
файле `.env.groq`, выставь `GROQ_ACTIVE_SLOT` в 1, 2 или 3 и перезапусти сервер.
Пустой `GROQ_ACTIVE_SLOT` сохраняет обычную настройку из `.env` или окружения.
Файл `.env.groq` исключён из Git.

При HTTP 429 сервер учитывает заголовок `Retry-After` и показывает срок
ожидания в чате. Лимиты Groq действуют на уровне организации.

## Проверка диалога без токенов

Из корня репозитория запустите:

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_chat_dialogue -v
```

Тесты используют реальные обработчики чата и расчёт правил с подменёнными ответами модели. Они проверяют уточнения, правки и сохранение существующей конфигурации. Модельные запросы для этого прогона не нужны.

Описание интерфейса и его оформления находится в [материалах участника С](TZ_sajt_v_stile_sinoniks.md).
