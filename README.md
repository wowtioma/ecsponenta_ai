# Экспонента · Синоникс

Веб-ассистент для предварительного проектирования контролируемого обмена между двумя сетями через ПАК «Синоникс».
Кейс «ИИ-ассистент по размещению Синоникса», АйТи Бастион · НЭТИ-НЕКСТ 2.0.

## Задача

Между офисной сетью и закрытым сегментом цеха нужен контролируемый обмен, прямое соединение сетей запрещено.
Инженер разбирает обращение вручную: выясняет параметры, выбирает размещение «Синоникса», считает минимальный
набор правил и рисует схему. Готовая анкета не подходит — заказчик не знает протоколов и терминов.

Мы прочитали задачу так: это не чат-бот про «Синоникс», а проектировщик обмена — от свободного текста до схемы,
которую инженер проверит и заберёт в draw.io.

## Что сделали

**Диалог.** Пользователь описывает сети обычным текстом. Ассистент задаёт уточняющие вопросы карточками
(варианты, «Не знаю», «Другое»), не повторяет уже сказанное, не выдумывает IP, порты и протоколы.
Неизвестное остаётся в `unknowns`, согласованное — в `assumptions`.

**Расчёт.** Размещение: открытая сеть → МЭ на границе закрытого сегмента → «Синоникс» за ним; Узел А к открытой
сети, Узел В к закрытой, USB только к Узлу А. Правила данных: объединение потоков с общим получателем, портом
и протоколом, двунаправленные правила для MQTT, Modbus TCP и МЭК 104, NTP как одно однонаправленное UDP-правило,
лимит 256. Файлы: проверки сторон, совместимость PULL/PUSH, файловые пользователи без дублей.
Четыре статуса результата: `needs_clarification`, `preliminary`, `completed`, `unsupported`.

**Правки после результата.** Вопрос о схеме не меняет проект. Допустимая правка обновляет таблицу, схему,
служебный JSON и `.drawio`; недопустимая объясняется, последнее корректное решение сохраняется.

**Вход и экспорт.** В одном экране: объяснение, таблица правил из девяти колонок с обоснованием, схема
(одна модель даёт SVG на экране и XML для draw.io), редактор draw.io во вкладке, служебный JSON,
токены и стоимость сессии. Чёрно-белая тема с переключателем светлая/тёмная.

**Модель и знания.** Извлечение фактов из текста через Groq `openai/gpt-oss-20b` (OpenRouter, Yandex, GigaChat —
профили в конфиге), ответ с цитатой «файл + раздел» из базы знаний, журнал вызовов и стоимость по каталогу OpenRouter
(вход $0.075, выход $0.30 за 1 млн токенов). Модель понимает текст, правила считает детерминированное ядро —
результат воспроизводим. Неподдерживаемые запросы объясняются и фиксируются в `requests_for_vendor`.

## Структура

| Путь | Что внутри |
|---|---|

## Запуск

Нужны Python 3.10+, Node.js 20+ и ключ Groq. Создайте в корне `.env`:

```dotenv
LLM_PROVIDER=groq
GROQ_MODEL=openai/gpt-oss-20b
GROQ_API_KEY=<ваш ключ>
```

API (первый терминал):

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe integration_test_server.py
```

Интерфейс (второй терминал, из корня проекта):

```powershell
cd frontend
npm.cmd ci
$env:VITE_USE_MOCK = 'false'
npm.cmd run dev
```

Откройте адрес Vite. Порт 8000 занят — задайте `SYNONYX_API_PORT` для сервера и `SYNONYX_API_TARGET` для Vite.
Другой комплект кейса — через `SYNONYX_BASE_DIR` или `SYNONYX_CASE_ZIP`.

## Проверки

```powershell
python -m unittest discover
python scripts/check_groq.py
python scripts/audit_integration.py   # нужен SYNONYX_CASE_ZIP
```

Состояние на сегодня: 141 тест проходит, эталоны F01, F02, F04, F07 совпадают, TypeScript и сборка Vite проходят.
При HTTP 429 клиент повторяет запрос на следующем ключе Groq из `.env.groq`.

## Известные ограничения

- Правки схемы в редакторе живут в браузере и входят в скачиваемый `.drawio`; на сервере они не сохраняются.
- Встроенный редактор draw.io требует доступа к `embed.diagrams.net`; без него доступны режим «Просмотр» и скачивание.
- Проектирование рассчитано на две сети и один «Синоникс»; запросы на большее объясняются и фиксируются.
- Отдельный замер времени и стоимости каждого шага для жюри пока не оформлен.
