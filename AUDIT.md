# Проверка интеграционной сборки, 22 ноября 2026

Проверен веб-проект из трёх частей команды. ТЗ, эксплуатационные сценарии, пример служебного JSON и 16 слайдов организаторов использованы как критерии. В живых диалогах работал Groq с моделью `openai/gpt-oss-20b`. Результаты ниже относятся к указанным прогонам. Ответы на закрытые задания и итоговый балл команды неизвестны.

## Проверки U01–U06

| Сценарий | Наблюдаемый результат |
| --- | --- |
| U01 | Два встречных правила SFTP. У отправителя каждого правила PULL, у получателя PUSH. Рассчитано два технических пользователя. В этом прогоне проект завершился с пустыми списками проверок, хотя заказчик указал только их одинаковость. |
| U02 | Первый вариант разделён на два правила по отделам, число людей уточняется отдельно. Во втором независимом варианте получено ноль готовых правил, нижняя оценка один, задан вопрос о хранилище автоматической доставки. Автоматической доставки заказчик не задавал. По сценарию ожидается одно правило. |
| U03 | В одной сессии успешно прошли вопрос о трёх компьютерах, добавление второго получателя, переименование, уточнение перед удалением и отказ открыть подсеть. Последовательность числа правил при изменениях — 1 → 2 → 2 → 1. Проверены ответы API и состояние. Скачивание обоих файлов после каждого шага этого диалога отдельно не измерялось. |
| U04 | При трёх сетях предложено выбрать пару, получен статус `unsupported`. При двух открытых сетях задан вопрос о защищаемой стороне. Ответ «Не знаю» сохраняет обе сети открытыми и `protected_network_id` в неизвестных, но текст объявил защищаемой сетью офис. |
| U05 | В Edge проверены повтор запроса, зум, возврат к целому виду и выгрузки JSON и XML. Два сохранённых ответа живого API (F02 и F07) воспроизводились в интерфейсе для этой проверки. В каждом XML — граф из отдельных редактируемых объектов. В F07 ребро USB соединяет носитель непосредственно с Узлом А. Встроенный редактор по внешнему адресу не подтвердил готовность. Ручное перемещение и сохранение объекта в нём остаются непроверенными. |
| U06 | Проверены уникальность записей, сумма токенов и оценка. Тест на уровне HTTP-клиента проверяет 429, повтор того же запроса и один учтённый успешный ответ. При отсутствии usage у отказа в отчёте остаются неизвестные значения. Два живых шага через Edge заняли 2,166 и 0,716 секунды до появления ответа. Этого недостаточно для зачётного среднего. |

В дополнительном диалоге о складе заморозки модель сохранила общий получатель журналов, нестандартные порты 15140 и 1502, инициатора Modbus и два встречных файловых потока. Уточнила только протокол доставки в закрытую папку. После ответа SMB получено четыре правила и два технических пользователя.

## Ядро, интерфейс и запуск

- `python -m unittest discover` — 128 тестов прошли. Проверки включают правила данных и файлов, границу 256, сессии, пакетные ответы, изменения проекта, поиск, учёт и поведение клиента Groq.
- `python verify_benchmarks.py <архив кейса>` — F01, F02, F04, F07 прошли с точным совпадением эталонов на структурированных данных. Это отдельная проверка от живых запросов, где модель сначала извлекает данные из текста.
- TypeScript, production-сборка Vite и ESLint прошли на установленных зависимостях. Сборщик предупреждает о четырёх отсутствующих файлах Formular и JS-пакете больше 500 кБ. Чистая установка фронтенда через npm в этом прогоне отдельно не проверялась.
- Проверен запуск API с базой из репозитория и из ZIP организаторов. Состав верхнего уровня живого результата F02 совпал с предоставленным `result.example.json`. Это сравнение структуры одного результата.
- При HTTP 429 сервер пробует следующий настроенный ключ для той же модели. Средства защиты от повторов проверены с одним ключом, с тремя, с исчерпанием всех, с восстановлением и с ошибкой другого типа. В живом прогоне встречались реальные 429, в том числе после обращения к нескольким ключам. Квота организации может быть общей. [Документация Groq](https://console.groq.com/docs/rate-limits)

## Что подготовить для защиты

1. **Повторить F07, U02 и вопросы о лимите с разными формулировками.** Проверять весь путь от сообщения до правил. В F07 ошибку показывает уже структура потока. В перефразировке Q01 причина видна в результатах поиска. Для N01 и U04 нужна отдельная проверка утверждений в тексте по полям `unknowns`.
2. **Записать единый прогон времени и стоимости.** Сейчас интерфейс меряет пользовательский шаг, а серверный `timing` строится по времени модельных вызовов. Серверный JSON пропускает шаги без вызова модели и время отрисовки. Для жюри нужен журнал каждого шага до готового результата, включая ошибки и повторы, и отдельная запись подготовки ключевого индекса с нулём модельных вызовов. Разбивка расходов по моделям есть в серверной сводке. Интерфейс показывает список моделей и суммарные расходы.
3. **Зафиксировать модель и вариант провайдера.** На момент сверки Groq для 20B стоит $0,075 за вход и $0,30 за выход за миллион токенов. Для 120B у того же провайдера — $0,15 и $0,60. При пределе входа $0,10 для защиты подходит проверенная конфигурация 20B. Окончательные ставки организаторы фиксируют общим снимком. Фактического списания Groq в проверенных ответах не было. [20B](https://openrouter.ai/openai/gpt-oss-20b) · [120B](https://openrouter.ai/openai/gpt-oss-120b)
4. **Открыть экспорт на машине защиты.** Проверить в draw.io переименование блока, его перемещение, сохранение и повторное открытие. Убедиться, что обе сети, МЭ, Узлы А/В и USB остаются читаемыми при проекции. Просмотр схемы и скачивание работали и без готового внешнего редактора.
5. **Собрать комплект сдачи.** В презентации организаторов на слайде 15 перечислены воспроизводимый запуск, зависимости, модель и тарифы, несколько пар JSON/.drawio, выгрузка вызовов и времени, архитектура и ограничения. Для командной презентации добавить свои скриншоты и один живой диалог U03 с добавлением, переименованием и удалением получателя. Запросы поставщику входят в JSON проекта, отдельной общей выгрузки по сессиям в интерфейсе не обнаружено.

Публичное размещение приложения — отдельный этап. Для этих результатов использован локальный запуск.
